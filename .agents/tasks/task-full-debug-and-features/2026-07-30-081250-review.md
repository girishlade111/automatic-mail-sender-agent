# Full-stack overhaul: bug fixes, templates, analytics, scheduling, and tests

This change rewrites most of the backend and frontend of an AI email outreach agent. The backend gains proper logging, a closure-fix in Celery tasks, new CRUD endpoints for email templates, campaign duplication/update/analytics/export/scheduling endpoints, paginated logs, and email validation via DNS MX lookups. The frontend adds corresponding pages and hooks (templates management, analytics dashboard, campaign edit, paginated logs, search/filter, schedule dialog, export CSV), plus shadcn `Select` and `Progress` components. Docker Compose gets healthchecks and restart policies. 30 backend tests are added covering the new endpoints.

**Watch for:** A confirmed frontend/backend field mismatch on the validation response (`total` vs `validated`) will cause the validation success message to show "undefined" (confirmed). A React key warning in the preview table's expandable rows uses bare fragments inside `.map()` (confirmed). The scheduling system stores a `scheduled_at` timestamp but has no background process to actually trigger the send at that time (confirmed). The settings page hardcodes rate-limit numbers that don't match the backend config (confirmed).

**Verdict**: NEEDS_CHANGES

## High-level view

The closure bug in Celery tasks — a lambda-in-a-loop capturing stale loop variables — is replaced with `functools.partial` binding concrete values before passing to `with_retries`.

Templates, analytics, scheduling, validation, duplicate, update, and export together form the new API surface. The scheduling endpoint stores a timestamp and sets campaign status to "Scheduled", but no Celery Beat schedule or polling task exists to check when the scheduled time arrives, making it a dead feature at runtime.

The frontend/backend contract has a field-name mismatch on the validation endpoint: the backend responds with `total` but the frontend `ValidationResult` type expects `validated`. The preview page also renders expandable email bodies inside a bare `<>` fragment with no key, which will trigger React console warnings and can cause row-state bugs when the list re-renders.

The settings page displays hardcoded rate-limit values (20/min, 500/day, 5s delay) that don't correspond to the backend's actual configuration (50/hour, 400/day, 20s default delay). Users reading this page will get a false picture of their sending limits.

The test suite covers 30 happy-path cases. Coverage is thin on error paths (no tests for rate-limit enforcement, schedule validation, export, or the logs endpoint) but provides a solid foundation.

## Closure fix via `functools.partial`

The original code passed `lambda: generate_personalized_email(...)` to `with_retries` inside a for-loop. The lambda captures variables by reference, so by the time the retry function executes, `contact_data` could reference a different loop iteration's state. The fix extracts `_generate_email_for_contact` and `_send_email_for_contact` as module-level helpers and uses `partial` to freeze the arguments before entering `with_retries`.

The top-level `except Exception` blocks added to both tasks re-raise after logging, which means Celery's `max_retries=3` will kick in for unexpected crashes. Previously, unhandled exceptions in the task body would propagate without any log entry.

## Validation endpoint field mismatch

The backend `validate_campaign_contacts` returns:

```python
return {
    "message": "Validation complete",
    "total": len(contacts),
    "valid": valid_count,
    "invalid": invalid_count,
}
```

The frontend `ValidationResult` type expects:

```typescript
export interface ValidationResult {
  message: string
  validated: number  // <-- mismatch
  valid: number
  invalid: number
}
```

And the preview page reads `result.validated`, which will be `undefined`, producing "Validated undefined contacts: 0 valid, 0 invalid" in the UI.

## Schedule without trigger

The `schedule_campaign` service sets `campaign.scheduled_at` and `campaign.status = "Scheduled"`. The endpoint enforces that `scheduled_at` must be in the future and only Draft/Generated campaigns qualify.

However, there is no Celery Beat periodic task, no polling loop, and no mechanism that checks `WHERE scheduled_at <= now() AND status = 'Scheduled'` and fires `send_campaign_emails_task`. The scheduling feature records the user's preference but will never execute the campaign. The frontend's Schedule dialog successfully sets the date but the campaign will sit in "Scheduled" status indefinitely.

## React key warning in preview table

```tsx
{valid.map((c) => (
  <>
    <TableRow key={c.id}>...</TableRow>
    {expandedBody === c.id && c.body && (
      <TableRow key={`${c.id}-body`}>...</TableRow>
    )}
  </>
))}
```

The outermost element returned by `.map()` is a bare `<>` fragment with no key. React's reconciliation requires the key on the top-level element. This causes a console warning and can lead to incorrect row state when the list re-renders (e.g., expanding one row while another is already expanded).

## Hardcoded rate-limit display

The settings page renders:

```
20 emails per minute
500 emails per day  
5s default delay
```

The backend config:

```python
MAX_EMAILS_PER_HOUR: int = 50
MAX_EMAILS_PER_DAY: int = 400
# campaign default: delay_seconds = 20
```

None of the frontend values match. There's no API endpoint that exposes the actual limits, so the frontend has no source of truth. The page misleads operators into thinking they have a 500/day budget when they actually have 400.

## Test coverage gaps

Not tested: the rate-limiting logic in `send_campaign_emails_task`, the scheduling service's future-time validation, the CSV export endpoint, campaign analytics, the email validation service's DNS lookups, the `regenerate_email` endpoint, the logs pagination endpoint, and error scenarios (e.g., updating a campaign in "Sending" status returns 400).
