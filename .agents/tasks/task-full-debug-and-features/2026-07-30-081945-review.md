# Full-stack overhaul: bug fixes, templates, analytics, scheduling, and tests (v2)

This is the v2 review pass. The six issues raised in v1 have all been addressed: the backend validation endpoint now returns `validated`, the preview table uses `React.Fragment` with a key, a Celery Beat periodic task (`check_scheduled_campaigns_task`) triggers due campaigns every 60 seconds, the settings page displays correct rate-limit values (50/hr, 400/day, 20s), the logs filter includes "Generated", and the dead `campaign_id` parameter was removed from `_sent_count_since`.

One new confirmed bug remains: the analytics page double-multiplies `delivery_rate` by 100, producing values like 7500% instead of 75%. A second concern involves the scheduled campaign trigger always selecting the first available Gmail account rather than allowing user selection at schedule time.

**Watch for:** Analytics delivery-rate display will show values 100x too large (confirmed). Scheduled campaigns always use the first Gmail account regardless of which account the user intended (likely). Schedule timestamps are interpreted as UTC regardless of user timezone (confirmed).

**Verdict**: NEEDS_CHANGES

## High-level view

The delivery-rate calculation in the analytics backend endpoint already returns a percentage (e.g., 75.0), but the frontend analytics page multiplies it by 100 again before displaying, producing nonsensical values. This is visible in the "Delivery Performance" section of the analytics dashboard.

The scheduling system is now functional end-to-end: the Beat schedule polls every 60 seconds and triggers `send_campaign_emails_task` for due campaigns. However, it arbitrarily picks `db.query(GmailAccount).first()` as the sender for all triggered campaigns. If a user has multiple Gmail accounts, the scheduled campaign may send from an unintended account.

The schedule dialog constructs the timestamp as a naive string (`${date}T${time}:00`) with no timezone indicator. The backend treats naive datetimes as UTC. If the user is in a non-UTC timezone, the campaign will trigger at a different wall-clock time than expected.

## Analytics delivery_rate double-multiplication

The backend computes:

```python
delivery_rate = round((emails_sent / attempted) * 100, 1) if attempted else 0.0
```

This already produces a percentage value (e.g., 75.0 for 75%). The frontend analytics page then does:

```tsx
const deliveryPct = Math.round(analytics.delivery_rate * 100)
```

When `delivery_rate` is 75.0, `deliveryPct` becomes 7500, and the progress bar and label both display "7500%". The fix is either to remove the `* 100` on the frontend (treating the backend value as already a percentage) or change the backend to return a 0-1 fraction.

## Scheduled campaign Gmail account selection

The `check_scheduled_campaigns_task` picks the sender account with:

```python
gmail_account = db.query(GmailAccount).first()
```

This is a single global query unrelated to the campaign being triggered. If a user schedules a campaign intending it to send from their second Gmail account, the system will use whatever account happens to be first in the table. The Campaign model has no `gmail_account_id` field to store the user's choice, and the schedule dialog on the frontend doesn't expose an account selector.

For single-account setups this is invisible. For multi-account setups, emails will send from the wrong address with no way to control it. A `gmail_account_id` column on Campaign (or a separate scheduling table) would close the gap.

## Schedule timestamp timezone ambiguity

The frontend constructs the scheduled time as:

```tsx
const scheduledAt = `${scheduleDate}T${scheduleTime}:00`
// produces e.g. "2025-01-15T09:30:00" — no timezone indicator
```

The backend scheduler normalizes this:

```python
if scheduled_at.tzinfo is None:
    scheduled_at = scheduled_at.replace(tzinfo=timezone.utc)
```

A user in EST scheduling for "9:30 AM" will get a campaign that fires at 9:30 UTC (4:30 AM EST). The frontend should either append `Z` (and label the input as UTC) or include the browser's timezone offset using `new Date(...).toISOString()`.

## Logs filter missing "Sending" status

The `send_campaign_emails_task` writes log entries with status "Sending" (`log_queued = EmailLog(..., status="Sending",...)`), but the logs page filter dropdown doesn't include "Sending" as an option. Users can't filter to see in-progress transmissions.
